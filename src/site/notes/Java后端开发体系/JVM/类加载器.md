类加载器（`ClassLoader`）负责将类的二进制数据加载到 JVM 中。Java 允许使用：

- JDK 提供的类加载器；
- 开发者自定义的类加载器。

## 一、类的唯一性

一个类在 JVM 中是否相同，由以下两项共同决定：

> **类的全限定名 + 加载它的类加载器**

因此，即使两个类来自同一个 `.class` 文件，只要类加载器不同，JVM 也会将它们视为不同的类。

```
Class<?> c1 =
    Main.class.getClassLoader().loadClass("com.test.Test");

Class<?> c2 =
    new CustomClassLoader().loadClass("com.test.Test");

System.out.println(c1 == c2); // false
```

这两个类虽然名称和字节码相同，但类型身份不同。

因此，下面的类型转换会失败：

```
Test test = (Test) c2.getDeclaredConstructor().newInstance();
```

因为 `c2` 对应的 `Test` 是由自定义类加载器加载的，而变量声明中的 `Test` 通常是由应用类加载器加载的。

```
ClassCastException
```

### 结论

> **类加载器不同，即使类文件相同，也不是同一个类。**

这也是 Java 实现模块隔离、插件化和热部署的基础。

## 二、JDK 内置类加载器

JDK 默认提供了三个主要类加载器：

|类加载器|负责加载的类|
|---|---|
|Bootstrap ClassLoader|Java 核心类，如 `java.lang.String`|
|Platform ClassLoader|JDK 平台模块中的类|
|Application ClassLoader|应用程序的类，以及用户依赖的第三方类|

例如：

```
System.out.println(String.class.getClassLoader());
// null，表示由 Bootstrap ClassLoader 加载

System.out.println(Main.class.getClassLoader());
// Application ClassLoader
```

`Bootstrap ClassLoader` 由底层实现，Java 代码中通常显示为 `null`。

## 三、双亲委派机制

类加载器收到加载请求后，通常会先检查自己是否已经加载过；

如果没有，再采用**双亲委派模型**：

1. 当前类加载器先请求父类加载器加载；
2. 父类加载器无法加载时，才由当前类加载器尝试加载；
3. 如果所有加载器都无法加载，抛出 `ClassNotFoundException`。

### 阶段结果

双亲委派机制主要解决两个问题：

- **避免核心类被重复加载**，保证 Java 核心类的唯一性；
- **防止核心类被恶意替换**，提升 JVM 安全性。

例如，用户自定义一个 `java.lang.String`，也不会覆盖 JDK 自带的 `String`，因为请求会优先交给 Bootstrap ClassLoader。

## 四、自定义类加载器

自定义类加载器通常继承 `ClassLoader`，重写 `findClass`：

```
public class CustomClassLoader extends ClassLoader {
    @Override
    protected Class<?> findClass(String name)
            throws ClassNotFoundException {
        byte[] data = loadClassBytes(name);
        return defineClass(name, data, 0, data.length);
    }
}
```

其中：

- `loadClassBytes` 负责获取 `.class` 文件的字节数组；
- `defineClass` 负责将字节数组转换为 JVM 中的 `Class` 对象。

一般不建议直接重写 `loadClass`，否则可能绕过双亲委派机制。除非确实需要自定义完整的加载顺序。

## 0. 出发点：为什么不直接用文件系统 + Page Cache？

三个原因：双缓冲浪费内存；OS 只保证 4KB 原子写，数据库想要 16KB 单位，得自己防"写一半"；OS 的 LRU 挡不住全表扫描冲刷热数据。所以 InnoDB 在文件字节流上自建了空间管理和缓存两套体系。



## 1. 页（Page）：一切的起点

- **定义：磁盘 I/O 和内存缓存的最小单位，默认 16KB**，建实例时由 `innodb_page_size` 设定（4K~64K），之后不可改。
- **定位：页号只在表空间内唯一，全局定位 =（space_id，page_no）**，类比 OS 的（inode，offset）。
- **页 = B+ 树节点**：
	- 叶子页存行（数据）
	- 非叶子页存"键 + 子页号"目录；
	- 同层页用前后指针串成双向链表，支撑范围扫描。


## 2. 区（Extent）：连续的 1MB

- **定义：一组物理连续的页，空间批量分配的单位。**
- 尺寸：页 ≤16KB 时区固定 1MB（16KB 页即 64 页）；32K/64K 页时区为 2MB/4MB。
- **为什么需要：连续分配换顺序 I/O**——和 ext4 的 extent 名字相同、动机相同。叶子页物理相邻，范围扫描才是真的顺序读。
- **小表折中**：段的前 32 页逐页从碎片页里拿，满了才按整区分配。



## 3. 段（Segment）：按用途分组的逻辑单位

- **定义：一组区的逻辑集合，不要求物理连续。
	- **官方说法是"表空间文件里的文件"。



## 4. 表空间（Tablespace）：物理文件与页号命名空间

**定义：磁盘上的实际文件，是所有结构的容器，也是页号的命名空间。**

MySQL 8.0 有五种：

| 类型 | 文件 | 装什么 |
|------|------|--------|
| 系统 | `ibdata1` | Change Buffer、可选用户表 |
| 每表文件（默认） | `表名.ibd` | 单表数据+索引，DROP 可释放磁盘 |
| 通用 | 自定义 `.ibd` | 多表共享，路径灵活 |
| Undo | `undo_001/002`… | Undo 日志，8.0 起默认独立 |
| 临时 | `ibtmp1` | 临时表 |

**重要修正：** 老教程说 `ibdata1` 存数据字典、Undo、Doublewrite——8.0 里这三样已全部搬走（字典去 `mysql.ibd`，doublewrite 去独立文件，Undo 去 undo 表空间）。

---

## 5. 全景

```
表空间（文件 + 页号命名空间）
  └── 段（逻辑分组，区可不连续；每索引=叶子段+非叶子段）
        └── 区（1MB=64页，物理连续，换顺序I/O）
              └── 页（16KB，I/O与缓存单位，B+树节点）
                    └── 行（按主键串成链表，超长列溢出）
```

| 层级 | 性质 | 解决的问题 |
|------|------|-----------|
| 表空间 | 物理文件 | 隔离与运维 |
| 段 | 逻辑 | 按用途分类管理 |
| 区 | 物理连续 | 批量分配、顺序 I/O |
| 页 | 物理+逻辑 | I/O 与缓存单位 |
| 行 | 逻辑 | 数据本身 |

---

## 6. 内存侧：Buffer Pool

- **本质：InnoDB 自建的 Page Cache**（不信 OS，所以自己干）。内存切成页框，一框装一页；常配 `O_DIRECT` 绕开 OS 缓存。
- **三条链表**：Free（空闲框）、LRU（淘汰）、Flush（脏页，按修改先后排序供刷盘）。
- **改良 LRU：分 young（5/8）+ old（3/8）两段**，新页插到 old 头部，须在 old 区停留超 1 秒且再次被访问才晋升 young——全表扫描的页熬不到晋升就被淘汰，热数据安全。思路和 Linux 的 active/inactive 双链表一致。
- **chunk 是 Buffer Pool 在线扩缩容的单位（默认 128MB），和磁盘侧的区毫无关系。**

---

## 7. 页的一生

```
读：缺页 → 读16KB入Buffer Pool（可整区预读）→ 插入old区头部
改：内存修改 → 变脏页 → 先记redo日志（WAL）
刷：后台线程批量写回 → 先写doublewrite，再写真实位置
淘汰：干净页直接丢，脏页先刷后丢
```

- **redo（WAL）**：先记日志再慢慢刷脏页，把随机写变成顺序写，解决"刷得慢"。
- **doublewrite**：脏页先写一份完整副本再写原位，解决 16KB"写一半"（torn page）。

---

## 8. 与 OS 对照

| OS | InnoDB |
|----|--------|
| 页 4KB | 页 16KB |
| (inode, offset) | (space_id, page_no) |
| ext4 extent | 区（1MB/64页） |
| Page Cache | Buffer Pool |
| active/inactive 链表 | young/old LRU |
| 文件系统 journal | redo + doublewrite |

一句话：InnoDB 不信任通用 OS 在数据库负载下的默认策略，于是在用户态把存储栈重造了一遍——但每一层都能在 OS 里找到对应物。

---

## 9. 一句话总结

**页是 16KB 的 I/O 与缓存单位，区是 1MB 连续空间换顺序 I/O，段按用途把区分组（每索引叶子/非叶子两段），表空间是装下一切的物理文件；内存侧 Buffer Pool 自建缓存，用 young/old LRU 防扫描污染，用 redo 和 doublewrite 分别解决"刷得慢"和"写一半"。**
